# Доработка PR #211 — BNP-158

## Issues/Notes

- Исправлена блокировка повторной оплаты после истечения Checkout: просроченный `PENDING` переводится в `CANCELLED`, освобождая уникальное ограничение на активный платёж.
- При конкурентной обработке устаревшей операции условное обновление защищает уже изменённый статус; конфликт уникальности при создании нового платежа преобразуется в `409 Conflict`.
- Блокирующий риск повторной отправки заказа в POS при неопределённом результате `POST` остаётся. Доступные адаптеры не подтверждают дедупликацию по внешнему ID и не дают проверить ранее созданный заказ. Без контракта провайдера нельзя гарантировать отсутствие дубликатов при сохранении повторов BullMQ.
- Открытые записи ревью в `pr_discussions_raw.json` не имеют `threadId`/`rootCommentId`; четыре идентифицированных inline-потока уже разрешены. Адресные ответы для текущих записей сформировать нельзя. В контексте отсутствуют `ci_failures.md`, `ci_failures_full.log`, `pr_files.txt`, `ticket.md` и корневой `instruction.md`; требования сверены с `request.md`, инструкции — с `CLAUDE.md` и `.dmtools/agents/instructions/pr_rework/`.

## Approach

- Тестами сначала зафиксированы сценарии просроченного платежа и гонки изменения статуса.
- В `createCardPayment` просроченная операция закрывается условным `updateMany` до создания новой. Если другая транзакция уже изменила строку, запрос завершается конфликтом; нарушение уникальности при создании также возвращает конфликт вместо необработанной ошибки БД.
- POS-поведение не менялось: для безопасного устранения блокера требуется подтверждённая возможность идемпотентного создания или поиска заказа у используемого провайдера.
