# Доработка PR #211 — BNP-158

## Issues/Notes

- Блокирующий риск повторной отправки заказа в POS остаётся открытым. При таймауте или потере ответа невозможно понять, принял ли POS запрос; повтор может создать дубликат. В доступной конфигурации для r_keeper и iiko не найден подтверждённый контракт идемпотентности или API поиска заказа. Локальный флаг до `POST` исключил бы повтор, но мог бы навсегда оставить заказ неотправленным после сбоя до вызова POS. Для безопасного решения нужен подтверждённый контракт для обоих провайдеров.
- Исправлена документация bePaid: маршрут согласован с BNP-158, а 15-минутный срок платежной инициативы отделён от максимального 24-часового срока токена провайдера.
- В `pr_discussions_raw.json` inline-потоки 1–4 уже разрешены. Остальные нерешённые записи, включая новые замечания к документации, не содержат `threadId` и `rootCommentId`, поэтому сформировать адресные ответы невозможно. Файлы CI-ошибок, `pr_files.txt`, `ticket.md` и корневой `instruction.md` в подготовленном контексте отсутствуют; требования сверены с `request.md`.

## Approach

- Внесены только документальные исправления для маршрута и срока Checkout.
- Проверены POS отправка и адаптеры: внешний ID заказа передаётся, однако наличие этого поля само по себе не подтверждает дедупликацию. Production-код не менялся, поскольку без контракта провайдера любая локальная стратегия оставляет риск дублирования или потери заказа.
