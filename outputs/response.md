# Доработка PR #210 — BNP-157

## Issues/Notes

- Контракт API Оплати™ по-прежнему не подтверждён официальной документацией. В предоставленных материалах нет URL, схемы запроса/ответа и точных параметров webhook; до их получения реальную интеграцию нельзя считать готовой к эксплуатации.
- В комментарии к BNP-215 явно выбран вариант B: после оплаты не закрывать сессию и не менять состояние стола. Реализация следует этому согласованному решению, хотя исходный scope BNP-157 всё ещё упоминает обновление стола.
- Полный интеграционный сценарий оплаты через mock API и webhook не добавлен. Изменение защиты от второго активного платежа не покрыто отдельным регрессионным тестом; общие тесты проходят, но это поведение требует целевого теста.
- Файлы `ticket.md`, CI логов, `pr_files.txt` и корневого `instruction.md` в подготовленном контексте отсутствуют. Конфликт `outputs/response.md` разрешён заменой конфликтующего текста отчётом по BNP-157.

## Approach

- Перед вызовом провайдера создаётся запись `PENDING`. Частичный уникальный индекс запрещает второй активный платёж Оплати™ на заказ. Повторный запрос возвращает сохранённый QR, если создание уже завершилось, или ответ `409`, пока первый запрос ещё обрабатывается.
- Ошибки сети, ответа или его JSON переводят резервную запись в `FAILED`, чтобы она не блокировала повторную попытку.
- Consumer условно помечает заказ оплаченным только если он ещё не оплачен; обновление заказа и статуса платежа выполняется в одной транзакции.
- Миграция уникальности внешней транзакции переименована на timestamp после миграций, добавленных в текущую базу. Новая миграция активного платежа имеет более поздний timestamp.
