# Результат доработки PR #192 — BNP-481

## Issues/Notes

- Блокирующее требование BNP-481 остаётся невыполненным: `ShiftService.open` создаёт локальную смену без подтверждения открытия в СКНО, а `ShiftService.close` закрывает её и сохраняет локальный `shiftReport` без вызова кассы и получения фискального Z-отчёта.
- В репозитории и подготовленном контексте нет согласованного API/протокола или SDK СКНО. Без контракта нельзя безопасно реализовать фискальные запросы и обработку их ошибок. Для завершения нужны контракт/клиент СКНО и контролируемый интеграционный стенд.
- В `pr_discussions_raw.json` все 13 inline-тредов имеют `resolved: true`; более поздние сводки не содержат `threadId` и `rootCommentId`. Открытых адресуемых тредов нет.
- В подготовленном контексте отсутствуют `instruction.md`, `pr_files.txt`, `ci_failures.md`, `ci_failures_full.log` и `merge_conflicts.md`.

## Approach

- Обновил BNP-413 e2e-проверку: подтверждение сброса `dailyOrderNumber` идёт через следующий заказ, созданный публичным API с ожидаемым номером `1`; удалено дублирующее чтение поля напрямую через Prisma.
- Проверил наличие реализации или контракта СКНО в `apps/` и `packages/`. Найдены только реквизиты кассы и логи-заглушки.
- Производственную интеграцию СКНО не добавлял, поскольку протокол отсутствует. Целевой e2e подтверждает локальный цикл смены и нумерацию заказов, но не фискальные операции.
