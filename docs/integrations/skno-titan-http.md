# СКНО / КСА «Титан-А», «Титан-ПЛЮС» — HTTP-протокол кассы

Рабочая спецификация для интеграции смен (открытие/закрытие, Z-отчёт) с кассой
«Титан». Официальной публичной спецификации вендора для РБ нет; документ собран
из открытых источников (см. «Источники») и **требует проверки на реальной кассе**.

## Происхождение и степень уверенности

- Инструкция по подключению Титан-А / Титан-ПЛЮС к 1С (vial.by) показывает:
  касса поднимает встроенный HTTP-сервер (`LW-HTTP`) на локальном IP,
  HTTP Digest-авторизация, realm `HTROM`, заводской логин `service`.
- Ровно такой же транспорт, realm `HTROM` и логин `service` описаны в
  «Протоколе обмена для кассовых аппаратов "Хелп Микро"» — HTTP + JSON.
- Вывод: Титан, по всей видимости, работает на той же платформе/прошивке.
  Протокол «Хелп Микро» — базовая спецификация ниже.
- **Не покрыто:** специфика белорусского СКНО. В документе «Хелп Микро» вместо
  СКНО фигурирует модем налоговой Украины (ДПА); передача в СККО на Титане
  может отличаться. Коды ошибок и поля, связанные с модемом, не переносить
  как есть без проверки.

## Транспорт и авторизация

- HTTP/1.1, порт 80 кассы, тела запросов и ответов — `application/json`.
- HTTP Digest (MD5, `qop=auth`), realm `HTROM`.
  - Сервисный пользователь: `service` (заводской пароль задаётся на кассе;
    хранить в зашифрованных реквизитах tenant, не в коде).
  - Операторы (кассиры) — из таблицы `/cgi/tbl/Oper`, имя пользователя = номер
    оператора.
- Белый список IP без авторизации: таблица `/cgi/tbl/whiteIP`,
  регистрация текущего IP — `/cgi/proc/register`.

Пример:

```http
GET /cgi/state HTTP/1.1
Host: 192.168.8.2
Authorization: Digest username="service", realm="HTROM", nonce="...", uri="/cgi/state", algorithm=MD5, response="...", qop=auth, nc=00000001, cnonce="..."
```

```json
{"model":"CHIP 702","name":"CR00001234","serial":"CR00001234","time":1412063757,
 "chkId":0,"JrnTime":0,"currZ":11,"IsWrk":0,"FskMode":1,"CurrDI":64,"err":[]}
```

## Элементы протокола

| Операция | Запрос |
|---|---|
| Вызов процедуры | `GET /cgi/proc/<name>?p1&p2&...` |
| Чтение таблицы | `GET /cgi/tbl/<name>` |
| Изменение таблицы/строки | `PATCH /cgi/tbl/<name>[/<id>]` (или `POST` + `X-HTTP-Method-Override: PATCH`) |
| Добавление / удаление строк (только `PLU`) | `PUT` / `DELETE` (или `POST` + override) |

Форматы параметров процедур: число `12.5`, дата `YYYY-MM-DD`, время
`[T]HH:MM[:SS]`, бинарные данные `x0102AB`.

## Ресурсы, нужные для смен

| Ресурс | Назначение |
|---|---|
| `GET /cgi/state` | Состояние: `serial`, `currZ` — номер текущего дневного (Z) отчёта, `IsWrk`, `chkId` — id последнего объекта ленты, `JrnTime` — начало ленты, `err` |
| `GET /cgi/dev_info` | `dev_zn` заводской номер, `dev_fn` фискальный номер, `dev_nn` налоговый номер, `dev_ver` версия ПО |
| `GET /cgi/chk[?id=<id>]` | Чековая лента (JSON-массив), дочитка после `id` |
| `GET /cgi/proc/printreport?0` | **Z-отчёт** — дневной отчёт с обнулением |
| `GET /cgi/proc/printreport?10` | Дневной отчёт без обнуления (X-отчёт) |
| `GET /cgi/proc/printreport?1` | Повторная попытка передачи и очистки ленты, если при Z-отчёте обмен с сервером налоговой не прошёл |
| `GET /cgi/tbl/FDay` | Записи Z-отчётов в фискальной памяти: `id`, `Date`, `STax0..4`, `SRet0..4`, `NChk`, `NRet` |
| `GET /cgi/rep/pay` | Остатки по видам оплаты: `[{no, sum}]` |

### Что делает Z-отчёт (`printreport?0`)

1. Печатает отчёт.
2. Переносит итоги дня в фискальную память (новая строка `FDay`).
3. Инициирует передачу данных в налоговую.
4. При успешной передаче очищает электронную ленту.
5. При ошибке передачи лента **не** очищается; повтор — `printreport?1`.

### Открытие смены

**Отдельной процедуры «открыть смену» в протоколе нет.** Смена начинается с
первой операции после Z-отчёта: регистрации кассира (объект `L` в ленте) или
первого чека. Практическая трактовка для `ShiftService.open`:

- проверить `/cgi/state` (касса доступна, `err` пуст, серийный номер совпадает
  с `cashRegisterSerial` tenant);
- зафиксировать `currZ` на момент открытия;
- открытие считается подтверждённым, если касса ответила без ошибок.

Проверить на живой кассе, есть ли у Титана явная команда открытия смены
(возможно, специфика СКНО).

## Чековая лента

Объекты ленты: `L` — регистрация кассира, `Z1` — номер дневного отчёта, `F` —
фискальный чек, `R` — возврат, `IO` — служебное внесение/изъятие. Общие поля:
`id` (монотонно растёт), `datetime` (Unix-time), `oper_id`. У чеков: `no`,
`Pending` (ещё не напечатан).

Строки чека — объект с одним из полей:

| Поле | Смысл | Поля содержимого |
|---|---|---|
| `S` | продажа | `qty` (≤3 знака), `price` (≤2 знака), `name`, `code` (≤13 цифр), `tax`, `sum` |
| `D` | скидка/наценка | `sum` (минус = скидка), `prc`, `subt`, `tax` |
| `P` | оплата | `sum`, `no` (строка таблицы `Pay`), `rrn`, `card` |
| `IO` | внесение/изъятие | `sum` (минус = изъятие), `no` |
| `C` | комментарий | `cm` |

## Ошибки

Любая операция при ошибке возвращает поле `err`:

```json
{"err":"x25"}
{"err":{"e":"Error %i","p":[100]}}
{"err":{"e":"x25","f":"tax"}}
{"err":[{"e":"x25"},{"e":"x26"}]}
```

Код — `xNN` (hex). Примеры: `x01` цена не указана, `x25` нет бумаги,
`x31` пользователь уже зарегистрирован, `x87` ошибка фискальной памяти.
Полный список — приложение 1 исходного документа.

## Рекомендации к реализации

- Клиент кассы — отдельный адаптер за интерфейсом (open / close → Z-отчёт),
  `ShiftService` зависит только от интерфейса.
- Локальное состояние смены (`OPEN` / `CLOSED`, `ShiftReport`) фиксировать
  **только после** успешного ответа кассы.
- В `ShiftReport` сохранять номер Z-отчёта кассы (`currZ` / `FDay.id`).
- Тесты — мок HTTP-сервера кассы с Digest-авторизацией: успешный Z-отчёт,
  ошибка `err`, недоступность кассы, несовпадение серийного номера.
- Реквизиты кассы (IP/хост, пользователь, пароль, серийный номер) — в
  зашифрованных `paymentCredentials.skno` tenant.
- Касса в локальной сети ресторана, облачный API до неё напрямую не достанет.
  Нужен локальный агент/мост или белый список и проброс — это решение за
  архитектурой, в рамках задачи зафиксировать как открытый вопрос.
