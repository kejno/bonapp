# Оплати™ — оплата по QR на экране счёта

> **Статус: отложено.** Владелец пока не подключает Оплати™. Story BNP-508 и
> BNP-509 заблокированы и отвязаны от эпика, тест-кейс BNP-431 в Skipped,
> баг BNP-487 закрыт как отложенная функция. Документ сохранён как проект
> на случай, если решение изменится; в работу по нему сейчас ничего не берём.

Рабочая спецификация для вкладки «Оплати™» (`/order/:orderId/pay`, SCREEN_46).

**Публичной документации API Оплати™ нет.** Спецификация, тестовая среда и
ключи выдаются мерчанту при подключении. Поэтому документ описывает только
то, что определено нашими требованиями (тест-кейс BNP-431, Story BNP-145,
решения BNP-249…252), и границу, за которой начинается неизвестное:
провайдер спрятан за интерфейсом `OplatiClient`, работа делится на две части.

1. **Гостевой поток и мок-адаптер** (Story «Оплата через Оплати™ по QR»).
   Полностью реализуется и тестируется без провайдера.
2. **Реальный адаптер** (отдельная Story, заблокирована до получения
   спецификации и песочницы от Оплати™).

Мок-адаптер входит в объём первой части и не считается «незакрытой
заглушкой»: без него гостевой поток нельзя проверить, а реальный вызов
подключается заменой адаптера без изменения остального кода.

## Что уже есть в репо

- Enum `PaymentMethod.OPLATI_QR`, модель `Payment` (`provider`,
  `providerTransactionId`, `status`, `payload`, `amountByn`, `tipsAmountByn`).
- Реквизиты `paymentCredentials.oplati`: только `merchantId`
  (`apps/api/src/tenant/payment-credentials.ts`).
- Гостевой API `guest/orders` с `GuestSessionGuard`; гость входит в комнату
  `order_<id>` событием `join_order_room`; статус заказа уходит в неё через
  `emitOrderStatusChanged` (`apps/api/src/menu/menu.gateway.ts`).
- `OrderStatusPage.tsx` уже слушает Socket.IO. `PayPage.tsx` вкладок оплаты
  не имеет.
- BullMQ используется в API; по CLAUDE.md платёжные вебхуки идут через
  очередь, не синхронно.

## Контракт (задан тест-кейсом BNP-431)

`POST /api/v1/guest/orders/:id/pay/oplati` (доступ по Table Session):

```json
{ "paymentId": "<uuid>", "qrCodeData": "<строка для QR>", "deepLink": "oplati://...", "expiresAt": "2026-09-30T12:15:00+03:00" }
```

- HTTP 200, `qrCodeData` и `deepLink` обязательны, `deepLink` начинается с
  `oplati://`.
- Повторный вызов для заказа с действующей попыткой возвращает её же, а не
  создаёт новую.

Экран: вкладка «Оплати™» показывает QR, кнопку «Открыть приложение»
(`<a href={deepLink}>`), обратный отсчёт до `expiresAt` и ожидание. **До
подтверждения об успешной оплате не сообщается.** После подтверждения
показывается «Спасибо! Приходите снова».

## Порт провайдера

```ts
interface OplatiClient {
  createPayment(input: {
    tenantId: string; paymentId: string; amountMinor: number;
    description: string; expiresAt: Date;
  }): Promise<{ providerPaymentId: string; qrCodeData: string; deepLink: string; expiresAt: Date }>;
  getStatus(providerPaymentId: string): Promise<'pending' | 'succeeded' | 'failed' | 'expired'>;
  cancel(providerPaymentId: string): Promise<void>;
  verifyWebhook(rawBody: Buffer, headers: Record<string, string>): { paymentId: string; status: 'succeeded' | 'failed' | 'expired' };
}
```

Форма интерфейса — наше предположение; реальный адаптер приводит ответы
Оплати™ к нему. Суммы в минимальных единицах (копейки), считать через
`Decimal`, не `float`.

### Мок-адаптер

- `createPayment` возвращает детерминированные `qrCodeData` и
  `deepLink = oplati://pay?payment=<providerPaymentId>`.
- `verifyWebhook` проверяет HMAC-SHA256 сырого тела по секрету из
  `OPLATI_MOCK_WEBHOOK_SECRET`; тесты подписывают тело тем же секретом.
- Выбор адаптера: `OPLATI_ADAPTER=mock|live` (по умолчанию `live`).
- **Мок не должен работать в production.** При `NODE_ENV=production` и
  `OPLATI_ADAPTER=mock` приложение не стартует. Пока реального адаптера нет,
  при `live` вкладка «Оплати™» не показывается (BNP-250: показываем только
  доступные способы), деньги фиктивно не принимаются.

## Поток

1. Гость открывает вкладку, клиент вызывает `POST .../pay/oplati`.
2. API создаёт `Payment` (`PENDING`, `OPLATI_QR`, `provider='oplati'`),
   вызывает `OplatiClient.createPayment`, сохраняет `providerPaymentId` в
   `providerTransactionId`, возвращает контракт выше.
3. Провайдер шлёт вебхук на `POST /webhooks/oplati/:tenantId` (публичный
   маршрут, без JWT). Обработчик проверяет подпись по сырому телу, ставит
   задачу в BullMQ и сразу отвечает `200`.
4. Воркер идемпотентно обновляет `Payment`; при `SUCCEEDED` завершает заказ
   существующим сценарием оплаты (`OrdersService.pay`) и шлёт статус в
   комнату `order_<id>`.
5. Клиент на событие переходит на «Спасибо!»; пока сокет не подключён,
   опрашивает `GET /guest/orders/:id` каждые несколько секунд.

## Решения (по BNP-249…252 и по умолчанию)

- **Сумма:** заказ плюс чаевые. Чаевые от 0,01 BYN до 100% заказа; до
  подтверждения кассового провайдера (BNP-252) чаевые не выпускаются,
  `tipsAmountByn = 0`.
- **Срок (BNP-251):** срок провайдера, запасной 15 минут; для Оплати™ на
  экране обратный отсчёт. После истечения или отмены: «Время оплаты
  истекло», кнопки «Повторить» (новая попытка, прежняя отменяется через
  `cancel`) и «Выбрать другой способ»; заказ остаётся открытым.
- **Запоздавший вебхук:** если провайдер сообщил `succeeded` уже после
  нашего истечения, оплата засчитывается (деньги списаны), `Payment`
  переходит в `SUCCEEDED`, событие логируется.
- **Идемпотентность:** по `providerTransactionId`; повторная доставка не
  меняет состояние.
- **Подтверждение гостю:** WebSocket с опросом как запасным путём.
- **QR на клиенте:** бюджет `guest-web` < 150 КБ. Либо лёгкая библиотека
  (до 5 КБ gzip), либо сервер отдаёт готовый SVG; выбрать по замеру размера
  бандла.

## Тесты

- Юнит: сервис оплаты с мок-клиентом (создание, повтор, истечение, отмена).
- Вебхук: верная подпись, неверная подпись, повторная доставка, запоздавший
  `succeeded`.
- e2e API по BNP-431: `pay/oplati` возвращает 200, `qrCodeData`, `deepLink`
  с `oplati://`; подписанный вебхук; заказ завершён; событие в WebSocket.
- Компонентный тест вкладки: QR, кнопка, отсчёт, отсутствие «успеха» до
  подтверждения, экран благодарности.

## Что нужно от Оплати™ для реального адаптера

- Спецификация API: создание платежа с QR / deeplink, запрос статуса,
  отмена, срок действия.
- Формат вебхука и способ проверки подписи.
- Схема авторизации и набор реквизитов мерчанта (помимо `merchantId`).
- Песочница и тестовые реквизиты. Секреты в репозиторий и тикеты не кладём.

Запрос на подключение должен подать владелец бизнеса.
